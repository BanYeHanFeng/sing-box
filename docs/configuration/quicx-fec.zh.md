# QUICX FEC：用纠删码抗丢包的可行性、设计与实测

本文回答一个问题：QUICX 能不能用"硬盘那种校验方式"（RAID 式的纠删码 / 前向纠错，FEC）
来扛丢包，从而不必像 Hysteria2 那样靠 `brutal` 拥塞控制"猛发大包"，同时又不浪费带宽。

结论：**可行，已经实现并在 CI 上用丢包链路验证通过**。核心设计是"按实测丢包率自适应冗余"：
链路不丢包时一个校验包都不发，丢包时冗余量跟着丢包率走，并且永远不超过配置上限。

---

## 1. 先明确：HY2 是怎么扛丢包的，代价在哪

Hysteria2 的 `brutal` 拥塞控制是"无视丢包，按固定速率发包"：

- 发送速率由用户手填（`up`/`down`），不随 ACK/丢包调整；
- 丢包不降速，靠 QUIC 重传补数据（因为发送方从不认为"网络拥塞"）；
- 代价是：速率填高了就持续超发（多余流量被链路丢弃，等于白烧带宽），
  填低了又跑不满；这种"恒定高速率 + 大量重传"的流量特征在 QoS/运营商侧也很显眼。

QUICX 现在（未开 FEC）用的是 BBR 类拥塞控制：丢包会被看到，会降速，重传还要等一个
RTT 量级的恢复时间。用户不想要 brutal，那我们就要在**不增加无谓流量**的前提下把丢包"补回来"，
这正是纠删码要做的事。

## 2. "硬盘的校验方式"是什么：从 RAID 到包级纠删码

- RAID 5：k 个数据块 + 1 个异或校验块，任意 1 块损坏都能算回来；
- RAID 6 / Reed-Solomon：k 个数据块 + m 个校验块，任意 m 块损坏都能算回来（GF(2^8) 上的线性方程组）。

把它搬到 QUIC 上，"块"就是**已经加密好的 QUIC 包（整包密文，含头部）**：

- 发送端把连续发出的 k 个 1-RTT 包编成一组，算出 m 个校验包（`m=1` 时就是纯 XOR，等价 RAID 5；
  `m≥2` 时是 GF(2^8) 上的 Vandermonde/RS 校验，等价 RAID 6），校验包本身也是普通 QUIC 包；
- 接收端缓存最近收到的包密文；收到校验包后，若发现组内缺包，就解出缺失包的**原始密文**，
  再把它丢回正常的解密/处理路径，和"真的收到了"完全一样；
- 于是这个包会被正常 ACK，发送端的丢包检测看不到它 —— 不重传、不降窗。

实现细节（可变长度是唯一的坑）：组内各包长度不同，异或前统一零填充到最长包，
每个包的长度随校验帧一起发（每个包 1~2 字节），接收端据此把恢复出的包截断回原始长度。

## 3. 为什么在 QUIC 里可行（关键工程点）

| 问题 | 处理方式 |
| --- | --- |
| 包号 / 头部保护 | 直接对**已封装好的整包字节**做校验，恢复出的是完整可解密的包 |
| 组内包长不一 | 零填充 + 长度表随帧发送 |
| 校验包不能超 MTU | 被保护的包限制为 `MTU - 头部预留`（`max_group_size=16` 约 63 字节），校验包 = 最长成员 + 头部预留 ≤ MTU |
| 恢复要赶在重传之前 | 接收端缓存最近约 `2×max_group_size` 个包；校验包在组结束后立刻发出，通常在丢包检测（≥1 RTT）之前到达 |
| 迟到/重复包 | 恢复出的包若与后到的真包重复，由 QUIC 原有去重逻辑丢弃 |
| 拥塞计费 | 校验包走正常发送路径，计入在途字节与拥塞窗口，只在发送循环允许时发出（**不绕过拥塞控制**） |
| 密钥更新 | 缓存按 key phase 失效即清空 |
| 后向兼容 / 伪装 | 不使用 QUIC 传输参数协商（否则 ClientHello 里会多出一个私有 TP，破坏 Chrome/HTTP3 指纹）；改为在 QUICX 自己的控制面协商，且不认识 FEC 帧的一端**忽略**而不是报错 |

## 4. 自适应冗余：怎么做到"不无脑堆带宽"

这是与 brutal 最本质的区别，也是本次实现的重点：

1. **接收端测信道丢包**：按 1-RTT 包号的空洞统计丢包率（与 FEC 是否开启无关，
   迟于 8 个包才判定为丢失，避免把乱序算成丢包）；
2. **每 20ms 回报一次**（累计计数，丢一帧反馈也不影响准确性）；
3. **发送端**：EWMA（α=0.3）平滑后取目标冗余 = `1.5 × 丢包率`，
   夹在 `[1/max_group_size, max_overhead_percent]` 之间，换算成分组大小 `k`；
4. **丢包 < 0.2% 时完全关闭**：`k=0`，一个校验包都不发（CI 已验证干净链路
   `ParityPacketsSent = 0`）；
5. **组尾保护**：分组空闲 2ms 未填满时，也为未满分组补发校验包，避免"最后一个包永远没保护"。

## 5. 开销数学

冗余 = `m / k`。单行（m=1）时：

| 实测丢包 p | 目标冗余 1.5p | 分组 k（上限 16） | 实际冗余 1/k | 组内 ≥2 丢包（FEC 修不全）概率 |
| --- | --- | --- | --- | --- |
| < 0.2% | — | 关闭 | 0 | — |
| 1% | 1.5% | 16 | 6.25% | 1.1% |
| 2% | 3% | 16 | 6.25% | 4.0% |
| 5% | 7.5% | 13 | 7.7% | 13.5% |
| 10% | 10%（封顶） | 10 | 10% | 26.4% |
| 20% | 10%（封顶） | 10 | 10% | 62.4% |

要点：

- 冗余粒度是 `1/k`，所以低丢包率（1~2%）下为了不超过 10% 上限，实际开销是丢包率的几倍
  （6.25% vs 1%）；把 `max_group_size` 调到 32 可以把下限压到 3.1%，代价是修复等待更久、
  突发丢包更容易落在同一组；
- 高丢包（>10~15%）时单行校验的"修不全"比例快速上升，此时 `max_parity_rows: 2`
  （RS 双校验）更有意义，但需要把 `max_overhead_percent` 放到 ≥ `2/max_group_size` 才会启用；
- 另有一项固定代价：开启 FEC 时被保护包的大小上限下调 40~130 字节（取决于 `max_group_size`），
  即单包有效载荷略降，属于"恒定少量开销"，与丢包率无关。不丢包时 FEC 关闭，这项目也不生效。

## 6. 与 HY2 `brutal` 的对比

| 维度 | HY2 `brutal` | QUICX FEC（本实现） |
| --- | --- | --- |
| 抗丢包手段 | 固定高速率 + 重传 | 纠删码前瞻冗余 + 少量重传兜底 |
| 带宽代价 | 与配置速率绑定，长期超发 | ≈ 实测丢包率（±1/k 粒度），上限可配 |
| 空闲/干净链路 | 仍按固定速率发 | **零冗余**，一个校验包都不发 |
| 拥塞控制 | 被绕过 | 正常参与，校验包也计入 cwnd |
| 恢复时延 | 1 RTT 量级（重传） | 校验包到达即恢复（通常是组结束后立刻） |
| 突发丢包 | 依靠重传 | 单行每组修 1 个；`max_parity_rows=2` 可修 2 个 |
| 可观测特征 | 恒定高速率流量，QoS 明显 | 与普通 QUIC 流量同构，仅多出少量小包 |
| 适用场景 | 弱网、丢包严重的跨境链路 | 同上，但更在意"别被 QoS 盯上/别白烧流量" |

## 7. 实现结构

三个仓库（均为 fork 分支）：

**quic-go**（`fec-dev`）

- `internal/wire/fec_frame.go`：两个私有帧
  - `FEC_REPAIR`（0x32）：`组号 | 行号 | 行数 | 包数 | 首包号 | 校验长度 | 包号增量表 | 长度表 | 校验数据`
  - `FEC_FEEDBACK`（0x33）：`收包数 | 丢包数 | 已修复数 | 修复失败数 | 校验包数`（累计值，丢帧无害）
- `fec.go`：GF(2^8) 运算、编码器（分组/校验/自适应控制器）、解码器（缓存/空洞测量/高斯消元恢复）、
  `Conn.EnableFEC/DisableFEC/FECStats` 公开 API
- `connection.go`：4 个钩子（发送后喂包、接收后缓存、FEC 帧处理、发送循环里发校验/反馈包）
- 测试：17 个单测 + 2 个端到端集成测试（真实 UDP + 丢包注入 + `-race`）

**sing-quic**（`fec-dev`）

- 协商：客户端在鉴权请求尾部追加 1 字节 FEC 能力位（老服务端会忽略多余字节）；
  服务端确认后在新的单向流上回 `CommandFECAccept`，双方各自 `EnableFEC`
- `quicx/fec.go`：`FECOptions`、能力位编解码、两端启用逻辑

**sing-box**（`fec-dev`）

- `option/quicx.go`：`inbound.fec` / `outbound.fec`（`max_overhead_percent` / `max_group_size` / `max_parity_rows`）
- `protocol/quicx/{inbound,outbound}.go`：把配置透传给 sing-quic
- 文档：本页 + quicx 出入站文档的 `fec` 字段说明

## 8. CI 实测数据（GitHub Actions）

- **quic-go FEC CI**（构建 + `go vet` + 单测 + `-race` 端到端）全绿；
- 干净链路 4MB 传输：`ParityPacketsSent = 0`（"不无脑堆带宽"的直接证据）；
- 丢包链路（注入 12.5% 丢包，实测约 20%~34%）：4MB 传输 10.7s 完成且数据校验一致，
  接收端 `RecoveredPackets` 数百个，发送端分组自适应到 4~7、冗余 14%~25%；
- 单测覆盖：单丢包恢复、双丢包恢复（RS 两行）、变长包、无可恢复、修不全计数、
  空洞丢包测量（含乱序/迟到）、自适应开/关/上限、GF(2^8) 乘法与求逆正确性。

## 9. 局限与后续

- 只保护 1-RTT 应用数据包；握手、0-RTT 不保护（握手阶段本身有重传兜底）；
- 校验包自身也会丢（丢包率 p 时，冗余的有效性约为 `1-p`），所以它是"提高到达率"而不是"保证到达"；
- 单行校验每组只能修 1 个丢包，突发丢包仍会退回 QUIC 重传；
- QUIC 流本身有重传，所以 FEC 对 TCP 流量的价值是**省掉一个 RTT 级恢复时延 + 避免拥塞控制误判**，
  而不是替代重传（对 UDP/DATAGRAM 中继，FEC 才是"唯一救命手段"，因为 DATAGRAM 永不重传）；
- 待评估：按 RTT 自适应分组大小、丢包突发度驱动的行数自动选择、真实移动网络实测、
  开启 FEC 时把 BBR profile 调保守（因为丢包已被修复，不必再激进）。
