### 结构

```json
{
  "type": "quicx",
  "tag": "quicx-in",

  ... // 监听字段

  "users": [
    {
      "name": "sekai",
      "password": "hello"
    }
  ],
  "udp_timeout": "",
  "idle_timeout": "",
  "heartbeat": "",
  "mtu": 0,
  "fec": {}
}
```

### 监听字段

参阅 [监听字段](/zh/configuration/shared/listen/)。

### 字段

#### users

quicx 用户。

#### users.password

==必填==

quicx 用户密码。

密码不上线：握手时两端各自用密码派生的密钥证明知道对方，服务端据此找到用户。

#### udp_timeout

NAT 超时时间

默认使用 `5m`。

#### idle_timeout

连接空闲超时时间

默认使用 `30s`。

#### heartbeat

发送心跳包以保持连接存活的时间间隔

默认使用 `10s`。

#### mtu

本端发出的包的最大长度，`1200` 到 `1452`。

默认为 `0`，即自动探测：连接建立后按地址族的默认值（IPv4 为 `1452`，IPv6 为 `1232`）发一个探测包，没有应答就退到下一档（`1400`、`1280`、`1200`），最多探测四次。探测包不占拥塞窗口，也不重传。

路径大小已知时填写它，探测就省下了：一条确定能过 `1280` 的隧道不必再从 `1452` 试起。

#### fec

前向纠错，保护本端发出的包。

服务端发出的是应答，客户端发出的是请求，所以这一项只覆盖应答方向；两个方向都要保护时，入站与出站都要配置。冗余包与数据包一样占拥塞窗口，因此它不会让链路更拥塞，只会把一部分带宽换成无需重传的恢复。

被冗余修复的包会按丢包上报给拥塞控制：数据到了，但路径确实丢了它，发送速率会因此降下来。这是有意的取舍——用冗余换到的不是"当没发生过"，而是"不用重传，但少发一点"。

```json
{
  "fec": {
    "enabled": true
  }
}
```

#### fec.enabled

==必填==

开启前向纠错。未开启时不能填写 `data_shards` 与 `parity_shards`。

#### fec.data_shards

一组包含的包数，`2` 到 `32`。

默认为 `32`。组越宽，冗余占的比例越小；覆盖 TCP 时 `32+2` 的尾延迟与带宽开销都优于 `10+2`。

#### fec.parity_shards

一组附带的冗余包数，`2` 到 `8`，且不超过 `data_shards`。

默认为 `2`。

### 说明

quicx 不是 QUIC：它运行在自己的 UDP 传输层上，不使用 TLS 与 HTTP/3，也没有对应的配置项。

握手是一来一回两个包，用密码与 X25519 派生的密钥认证并加密，之后的一切（包括 UDP 转发）都在同一个加密通道里，因此每个连接不重复握手，也不需要证书。

日志级别为 `debug` 时，每个会话每秒输出一行传输层数字：收发的包数与字节数、丢包、重传、被冗余修复的包、探测次数、在途包数、排队帧数，以及拥塞控制器的状态（模式、窗口、发送速率、带宽估计、最小往返）。
